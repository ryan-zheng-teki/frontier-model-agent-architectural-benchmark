001: # Payment execution independent of the customer order lifecycle
002:
003: ## Decision
004: Expose `OrderService.process_payment(payment_token, amount)` as the payment-only operation. It validates a positive amount, invokes `payment_gateway.charge(token, amount)` once, raises the existing payment-failure exception for unsuccessful results, and returns the successful gateway result unchanged.
005:
006: `process_order(order_id, customer_id, amount)` remains the customer workflow. It retains its early amount validation, active-customer check, pending-order check, paid-state persistence, receipt, and returned order. Its gateway execution delegates to `process_payment`, giving both workflows one charge/failure-handling implementation.
007:
008: The early amount check remains in `process_order` so invalid amounts still fail before database access. The payment-only boundary also enforces this inexpensive invariant; it does not repeat account validation or fraud scoring.
009:
010: ## Internal usage and trust boundary
011:
012: ```python
013: # Called only after the job has authorized and verified the enterprise account.
014: result = order_service.process_payment(enterprise_payment_token, invoice_amount)
015: # The caller owns subscription/batch accounting and lifecycle updates.
016: ```
017:
018: The method does not fetch customers or orders, inspect their status, change or save an order, or send a receipt. Internal callers supply the gateway token obtained upstream; no synthetic pending order is required. Existing constructor dependencies remain unchanged, but the payment-only operation does not access the database or notification service.
019:
020: This is an in-process capability for trusted callers, **not an authorization mechanism**. It does not verify corporate membership itself. Do not expose it directly as a customer-controlled endpoint. Eligibility, authorization, validation and fraud scoring remain upstream, as required. Ordinary customer requests continue through `process_order`.
021:
022: ## Why this shape
023:
024: - Payment execution and customer order orchestration have different responsibilities and return values. Separate operations make that distinction explicit.
025: - Flags such as `skip_validation`, `skip_pending_check`, or `send_receipt=False` would multiply workflow combinations and make accidental bypass easier.
026: - Copying gateway logic into a special enterprise method would allow error handling to drift.
027: - A subclass, strategy framework, or separate service hierarchy is unnecessary for this one-class module; a focused method extraction provides the required reusable boundary.
028: - The existing customer workflow is still supported behavior, not a legacy fallback. Both callers share one implementation of payment execution.
029:
030: ## Failures and limits
031:
032: Nonpositive amounts raise `ValueError("Amount must be positive")`. A failed gateway result raises `Exception("Payment failed: " + result.error)`. Gateway exceptions propagate unchanged. No retries are introduced: a retry could charge twice without a gateway idempotency contract. Failed payments must not advance customer order state or send receipts.
033:
034: No persistence migration, enterprise identity model, scheduler, batch loop, HTTP endpoint, currency conversion, or change to existing save/receipt failure recovery is included. Real gateway settlement is outside local tests.
035:
036: ## Verification
037:
038: Focused tests should establish payment-only success and failure with no DB/notification interactions, exact token/amount forwarding, positive-amount enforcement, and unchanged gateway exception propagation. Regression tests should establish existing customer validation ordering/messages, successful charge/save/receipt ordering and returned order, plus absence of state changes or notifications after failed payment.
